# 自動釣銭機プロトコルの「後差し込み」手順

本ソフトは、釣銭機の**制御プロトコルが未入手でも完成**するよう設計しています。
上位アプリ（会計ロジック・UI）は抽象I/F `ChangeMachine` にしか依存せず、
実機の通信仕様は **1ファイルに閉じ込め**てあります。

## 正直な前提

Glory RT-300／RTN-300／RT-380 系の「上位手順仕様書（外部インターフェース仕様）」は
**オープンに公開DLされてはいません**。ただし **Glory は公式の「接続サポート」窓口を持ち、
"つり銭機専用仕様書による開発"でレジベンダーに多数実績**があります（＝仕様書は存在し、接続支援として提供される）。
したがって：

- **シミュレータ**（`SimulatorChangeMachine.js`）で全機能が動作する状態にしてあります。
- 実機導入時に、下記いずれかの方法でプロトコルを把握し、**3点を埋めるだけ**で実機が動きます。上位は無改修。

## プロトコルの入手・把握ルート

1. **Glory 接続サポートへ問い合わせ**（`glory.co.jp/tsurisenki/connect_support/`）。実機オーナーとして
   通信仕様書の入手を打診。決済端末より現実的だが、非事業者は多少の摩擦/費用はあり得る。
2. **OPOS/JavaPOS ドライバ**があれば、生プロトコルを実装せずドライバ経由で制御できる可能性（要確認）。
3. **シリアル解析（リバースエンジニアリング）** — 実機が手元にある場合の実務。自分の所有機の正規操作なので問題ない。

### シリアル解析の進め方（ローカル環境＋USB-シリアル）

1. USB-シリアル変換で釣銭機に接続し、`DEBUG=1 npm start` で **RX/TX を全ログ取得**。
2. まず**電源投入直後**や**状態要求**に対する応答フレームを観測 → STX/ETX/長さ/BCC などの**フレーム構造**を特定。
3. **少額を1金種ずつ投入**し、投入検知フレームの差分から「入金額更新」電文を特定。
4. 「確定（釣銭払出）」「返却」を実行し、対応する要求/応答電文を特定。
5. 判明した値を `GloryRtChangeMachine.js` の `PROTOCOL` / `_buildFrame()` / `_onFrame()` に反映。
6. 異常系（詰まり・在庫不足・返却）を意図的に起こし、エラー電文も拾う。

> ※ロジックアナライザやシリアルモニタ（例：`interceptty`/`socat` でのポート二又）を併用すると、
> 既知POSと釣銭機の間の通信を観測でき、解析が速い。

## 差し込む場所（`backend/src/devices/changeMachine/GloryRtChangeMachine.js`）

1. **`PROTOCOL` 定数** … 状態要求／入金開始／確定（釣銭払出）／返却などのコマンドバイト列。
2. **`_buildFrame()` / `bcc()`** … フレーム構造（STX/本文/ETX/チェックサム）を仕様に合わせる。
3. **`_onFrame(buf)`** … 受信フレームを解釈し、以下のイベントを emit する：
   - 入金額更新 → `this.emit('deposit', { deposited })`
   - 払い出し完了 → `this.emit('dispensed', { change, breakdown })`
   - 返却完了 → `this.emit('refunded', { returned })`
   - 在庫/状態 → `this.inventory` を更新して `this._emitStatus()`
   - 異常 → `this.emit('error', { code, message })`

これらのイベント名・引数は**シミュレータと完全に同一**なので、上位のステートマシンは変更不要です。

## 実機への切替

`config.json`：
```json
"changeMachine": {
  "driver": "glory-rt",
  "serial": { "path": "/dev/ttyUSB0", "baudRate": 9600, "dataBits": 8, "parity": "even", "stopBits": 1 }
}
```
＋ `npm install serialport @serialport/parser-inter-byte-timeout`（optionalDependencies に定義済み）。

## 検証の進め方

1. まず**通信ログを取る**（`DEBUG=1 npm start` で TX/RX が出る）。
2. 状態要求→在庫レスポンスの往復が取れることを確認。
3. 少額の入金→確定→釣銭払出を、**現金を実際に入れて**1金種ずつ確認。
4. 異常系（詰まり・在庫不足・返却）をわざと起こしてイベントが上がることを確認。

> 仕様書が手に入らない場合でも、通信をロジックアナライザ/シリアルモニタで観測して
> リバースする方法はありますが、**整備業者・販社経由で正規に入手するのが確実**です。
